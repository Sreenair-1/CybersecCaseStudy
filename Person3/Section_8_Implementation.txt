Section 8 - Implementation Details

8.1 Safe Experimental Demonstration
This project implements a deterministic, non-destructive cybersecurity simulation. All agents, credentials, services, network zones, targets, attacks, detections, and containment responses are synthetic. The implementation does not perform real scanning, exploitation, malware execution, persistence, credential theft, or communication with external systems.

8.2 Synthetic Autonomous-Agent Environment
The experiment compares two local simulation environments. Environment A represents a baseline architecture with weak segmentation, broad credentials, limited monitoring, and greater resource visibility. Environment B represents a protected architecture with least privilege, credential isolation, network segmentation, policy enforcement, detection, and containment.

8.3 Synthetic Targets and Resources
Resources are defined in environment/resources.py. They include public resources, application services, internal services, database services, administrative services, credential stores, and sensitive resources. Each resource has a resource identifier, type, sensitivity level, owner, network zone, required role, required credential, and discoverability flag.

8.4 Baseline Security Configuration
The baseline environment intentionally allows broader credential/resource relationships, weaker network segmentation, and broader discovery. Baseline controls still record unauthorized behavior, but detection is delayed and containment is not applied.

8.5 Protected Security Configuration
The protected environment applies least privilege, credential isolation, strict zone transition rules, stronger policy enforcement, detection, and containment. Detected suspicious agents can be contained through a simulated BLOCK_AGENT action.

8.6 Autonomous Agent Attack Playbook
Attack behavior is represented as simulated event sequences: initial access, resource discovery, credential attempt, unauthorized access, lateral movement, and sensitive resource attempt. The playbook is implemented through action probabilities, profile risk tolerance, resource interests, permissions, credentials, topology, detection, and containment. Outcomes are not hard-coded.

8.7 Experimental Parameters and Trial Design
The default run uses seed 42, 100 attack trials per environment, 100 legitimate trials per environment, and a maximum of 18 steps per trial. Parameters can be changed through run_experiment.py command-line arguments.

8.8 Metrics Collected
The implementation calculates M1 resource discovery, M2 unauthorized actions, M3 lateral movement success rate, M4 sensitive resource exposure, M5 detection time, M6 containment time, M7 attack success rate, and M8 legitimate task success. Metrics are calculated from output/events.csv and written to output/metrics.csv.

8.9 Attack Graph and MITRE ATT&CK Mapping
The attack graph is generated from actual simulated transition events and saved as output/figures/attack_graph.png. The MITRE mapping is an explanatory abstraction only; it maps simulated stages such as discovery, credential attempt, lateral movement, and sensitive resource access to broad ATT&CK-style tactics without implementing real techniques.

8.10 Safety Controls and Isolation
The system uses only local Python objects and CSV/PNG outputs. Credentials are fake dataclass objects. Services and resources are simulated records. Containment changes simulation state only.

8.11 Software Architecture
The project is organized into agent, environment, security, simulation, and analysis packages. The entry point is run_experiment.py. Events are produced by simulation/trials.py, security decisions are handled by security modules, and metrics/figures are generated by analysis modules.

8.12 Synthetic Agent Profiles
The simulation includes five agent profiles: normal employee, privileged administrator, curious overreaching employee, compromised account, and service automation. These correspond to conservative, adaptive, exploratory, credential-oriented, and aggressive behaviors in the case-study framing. They are simulated profiles, not real autonomous malware.

8.13 Baseline/Protected Execution Flow
run_experiment.py initializes configuration, runs baseline trials, runs protected trials, writes events.csv, calculates metrics.csv, writes comparison.csv, generates figures, generates the attack graph, and prints a concise terminal summary.

8.14 Experimental Hypotheses
The expected hypothesis is that the protected architecture reduces unauthorized actions, lateral movement, sensitive-resource exposure, and attack success while preserving legitimate task completion.

8.15 Implementation Summary
The final implementation satisfies the Person 3 role by building the simulation, generating actual event data, calculating metrics from those events, producing figures, and packaging code/results for later use in Section 9. Numerical results must be taken from the generated CSV files and terminal output, not manually invented.
